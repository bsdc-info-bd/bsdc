# Launch audit

Generated by `node scripts/audit.mjs`. Every row below is produced by a
command that can be re-run on any commit; nothing here is a claim somebody
typed and nobody checked. The script exits non-zero if a single checkpoint
fails, so it can be wired into continuous integration the day anybody wants
it to be.

- **Pass** — the condition held when the audit last ran.
- **Recorded** — a measurement with no threshold. A count worth knowing that
  nobody should fail a release over.
- **Fail** — the condition did not hold. There are none at the commit this
  document was generated from.

## What the audit found, and what was fixed because of it

An audit that finds nothing has not been run properly. This one found four
real faults, all of them fixed in Response 20 and all of them now held by a
checkpoint so they cannot come back quietly:

1. **The verification portal had silently lost its head.** Re-running the
   corporate scaffold in Responses 18 and 19 overwrote `vf-site/index.html`
   with the generated stub, taking the title, description, canonical link,
   Open Graph tags and `WebSite` JSON-LD with it. The one indexable console
   had been de-indexed for two responses without a single test noticing. The
   head is restored and marked `bsdc:hand-written`; the scaffold now skips
   any file carrying that marker, and checkpoint E-10 asserts the canonical
   link is there.

2. **Thirteen consoles shipped with no security headers.** Only `main-site`
   had a `public/_headers` file. Every console now sends a content security
   policy with `script-src 'self'`, `frame-ancestors 'none'`, HSTS, a
   restrictive permissions policy and — for the eleven that are private
   tools rather than public pages — `X-Robots-Tag: noindex`. Checkpoints
   C-09, D-11, D-12 and D-13 hold that line.

3. **A floating dependency range broke the build and hid two bugs.** No
   lockfiles are committed, so a fresh `npm install` resolved
   `@supabase/supabase-js` 2.117 against a range written for 2.45. Its
   stricter insert typing immediately exposed two faults the looser types
   had been hiding: a product insert writing `image_url`, a column that does
   not exist on `public.products`, and a sketch update that tried to change
   its own owner. Both are fixed, and the client is pinned exactly in all
   fifteen packages (checkpoint I-06).

4. **Three type sizes were below the readable floor.** A 10px tab label is
   not legible on the 250px screen this interface promises to support. The
   screen minimum is now 12px, with the print stylesheet explicitly exempt
   because an href footnote on paper is not screen text (checkpoint C-27).

## What a program cannot check

Three things in this platform are matters of judgement, and they are
recorded here rather than dressed up as automated results.

**Whether the Bangla reads naturally.** A test can prove that both locales
carry the same keys and that the Bangla file contains 25,133 Bangla code
points. It cannot prove that a sentence sounds like something a person from
Sylhet would say. That needs a native reader, and it is the first thing to
put in front of one.

**Whether the honest answers are the right answers.** The platform refuses
to dress noise up as a forecast, reports speed at the 75th percentile with
its sample count, labels a route with fewer than twenty samples as not yet
worth believing, and tells a member why a moderation decision was taken. A
checkpoint can prove the code does these things. Only a person can decide
they are the right things to do.

**Whether the thresholds are right.** 250 KB of initial JavaScript, 4.5:1
contrast, a one-hour response target for a safety report, twenty samples
before a route is ranked: each is defensible and each is a choice. They are
written in one place each — the budget in CI, the contrast in
`domain/brand.ts`, the targets in `domain/moderation.ts`, the sample floor
in `domain/perf.ts` — so changing one's mind is a one-line change rather
than an archaeology project.
