# Launch audit

Generated by `node scripts/audit.mjs`. Every row below is produced by a
command that can be re-run on any commit; nothing here is a claim somebody
typed and nobody checked. The script exits non-zero if a single checkpoint
fails, so it can be wired into continuous integration the day anybody wants
it to be.

- **Pass** — the condition held when the audit last ran.
- **Recorded** — a measurement with no threshold. A count worth knowing that
  nobody should fail a release over.
- **Fail** — the condition did not hold. There are none at the commit this
  document was generated from.

## What the audit found, and what was fixed because of it

An audit that finds nothing has not been run properly. The first pass found
four real faults, all of them fixed in Response 20 and all of them now held
by a checkpoint so they cannot come back quietly:

1. **The verification portal had silently lost its head.** Re-running the
   corporate scaffold in Responses 18 and 19 overwrote `vf-site/index.html`
   with the generated stub, taking the title, description, canonical link,
   Open Graph tags and `WebSite` JSON-LD with it. The one indexable console
   had been de-indexed for two responses without a single test noticing. The
   head is restored and marked `bsdc:hand-written`; the scaffold now skips
   any file carrying that marker, and checkpoint E-10 asserts the canonical
   link is there.

2. **Thirteen consoles shipped with no security headers.** Only `main-site`
   had a `public/_headers` file. Every console now sends a content security
   policy with `script-src 'self'`, `frame-ancestors 'none'`, HSTS, a
   restrictive permissions policy and — for the eleven that are private
   tools rather than public pages — `X-Robots-Tag: noindex`. Checkpoints
   C-09, D-11, D-12 and D-13 hold that line.

3. **A floating dependency range broke the build and hid two bugs.** No
   lockfiles are committed, so a fresh `npm install` resolved
   `@supabase/supabase-js` 2.117 against a range written for 2.45. Its
   stricter insert typing immediately exposed two faults the looser types
   had been hiding: a product insert writing `image_url`, a column that does
   not exist on `public.products`, and a sketch update that tried to change
   its own owner. Both are fixed, and the client is pinned exactly in all
   fifteen packages (checkpoint I-06).

4. **Three type sizes were below the readable floor.** A 10px tab label is
   not legible on the 250px screen this interface promises to support. The
   screen minimum is now 12px, with the print stylesheet explicitly exempt
   because an href footnote on paper is not screen text (checkpoint C-27).

A second pass then went over the member publish path and the database's own
access control, driving the schema against a real database as `anon` and
`authenticated` rather than reading policy text. It produced five more
faults, each reproduced before it was fixed and each now held by a test or a
workflow:

5. **The PostgREST role channel and the application role travelled on one
   claim.** A console token must carry `role: 'authenticated'` or PostgREST
   refuses to map the call onto a database role at all; the same `role`
   claim was also being read as the member-facing application role. One
   value cannot safely mean both. The application role now travels on its
   own `bsdc_role` claim (migration 0036 plus the console claims reader),
   and `scripts/rls-proof.sql` asserts both channels resolve correctly for a
   member and for staff.

6. **Compose could report a loss as a save, and a missing profile as a
   crash.** A post whose write failed could be acknowledged as if it had
   been stored, and the database's response to a missing profile row reached
   the member as a raw error rather than a route to onboarding. The write
   path now fails honestly — an unsaved post is an error with the draft
   kept, and a missing profile redirects to onboarding — and the unit tests
   for both fail against the old behaviour.

7. **The member row existed only if onboarding had already finished.** Every
   post, comment and follow carries an author foreign key onto
   `public.profiles`, and onboarding was the only code path that ever
   created one, so a member who had not completed it could not persist
   anything. First sign-in now bootstraps the bare row — `uid` and a display
   name, every other column left to the database defaults, a true no-op on
   every later sign-in — proved against a live database as `authenticated`,
   and the insert's type was aligned with the columns the database itself
   defaults so a client cannot be type-checked into writing its own tuned
   values. The same pass closed out what gating onboarding means: an
   exported-but-unused `selectNeedsOnboarding` selector implied a client-side
   rule that no code upheld and the database never did, so it was removed
   rather than wired in — the gate is the sign-in redirect and the honest
   compose error, with the foreign key underneath both.

8. **A member could mint themselves a database role on their own profile
   row.** `public.profiles` was given a table-level INSERT grant, and in
   Postgres a table-level grant covers every column — including `role`.
   Because corporate authorization is deliberately database-driven, a
   brand-new member could insert their own row with `role = 'admin'` and
   have `bsdc.actor_role()` return `admin` and `has_permission('moderation.read')`
   return true, proved end to end on a live database as `authenticated`.
   Migration 0037 revokes the blanket grant and re-grants INSERT on exactly
   the self-service columns; `scripts/rls-proof.sql` fails the pre-0037
   schema on exactly this line and the Database workflow runs it on every
   schema change. One adjacent finding was recorded rather than changed:
   `public.reports` denies SELECT at the grant layer even though a select
   policy exists, so reads can only ever travel through the security-definer
   `moderation_queue()` — the secure default, left as it was found.

9. **Two publishers could race production, and the secret-scan allowlist
   silenced nothing by accident.** `deploy.yml` and Cloudflare's own Git
   builds were both able to publish, and a connected Cloudflare build has
   none of the GitHub secrets, so it could ship an unconfigured site that
   still looked like a success; `scripts/check-deploy-env.mjs` now fails the
   workflow build early, naming every missing `VITE_*`, and `deploying.md`
   records that the workflow is the single publisher and connected builds
   must be disconnected. And the `.gitleaks.toml` allowlist had escaped its
   path regexes twice inside TOML literal strings, so it had never matched a
   file — the escaping is fixed and the config now says why the entries
   exist.

10. **The Play Store submission had no way to delete an account.** The privacy
   policy had promised, since the day it was written, that a member could ask for
   their account to be deleted — and the only way to do it was to email support.
   Google Play requires an in-app path, so this was both a policy violation and a
   promise the product did not keep. `public.delete_my_account()` (migration
   0119) now deletes the member's content, social graph, behavioural traces,
   private records and device tokens, strips and suspends any vendor or shop row,
   scrubs finished orders, and leaves a tombstone profile so the order records the
   other party still needs keep resolving without identifying anyone. Both clients
   call it, `scripts/db-prove/t78.mjs` proves it from the database side (41 checks,
   including that a one-line omission from the delete list turns it red), and
   `src/test/delete-account.test.ts` holds the ordering the two systems force.
   The same pass found the terms of service had never existed as a page — the
   footer linked a policy and no terms — and that the Android app linked neither;
   `/terms` is now bilingual and tested, both are linked from the footer, and the
   app opens both in a custom tab beside its own delete-account flow. The data
   safety answers a Play reviewer asks for are written down against the schema in
   `docs/play-store-compliance.md`, and checkpoints K-01 to K-06 hold the four
   requirements rather than a document claiming them.

### Findings from the last full pass

Each of these was a live defect found by running the checks rather than by reading
the code, and each is now fixed with a test or a check that would catch it again.

- **Image priority was never set.** Every page hero carried `loading="eager"` and
  still lost the race, because eager loading moves a request earlier in time and not
  earlier in the browser's queue. `fetchpriority="high"` appeared nowhere in the
  source. `MediaImage` now takes one `priority` prop that sets both, so a caller
  cannot set half of the pair.
- **The product hero bypassed image recovery entirely.** `MarketProductPage` rendered
  a bare `<motion.img>`, so the one picture a buyer came to see had no retry ladder,
  no `srcset` and no edge-proxy fallback while the thumbnails around it recovered.
  Same for `ProductCard` and the vendor catalogue — the two most repeated images in
  the marketplace.
- **Every product thumbnail downloaded the full-size original.** The upload endpoint
  has always returned a ~640px variant, and `mk_products` kept only the original.
  Migration 0116 stores the variant map and emits it from the three read models;
  the existing arrays are untouched.
- **Editing a product would have erased its variants.** The edit form opened without
  the map and saved it empty, so correcting a name would have quietly undone 0116.
  Removing a picture also left its variant behind.
- **Five tables' `updated_at` never advanced.** `mk_cart_items`, `mk_settings`,
  `mk_credit_packages`, `admin_saved_macros` and `topic_affinity` had the column and
  no touch trigger, so an edited package price was indistinguishable from a seeded
  one. Migration 0117 installs the missing triggers.
- **Shop types and the checkout stepper used emoji as chrome.** Device-dependent
  pictures, font-dependent baselines, and announced as words to a screen reader; the
  pencil was a text-presentation glyph that renders as an outline on some builds.
  Replaced with vector icons that inherit `currentColor`.
- **The deploy workflow raced the deployment it was checking.** The upload-endpoint
  assertion was the one check in its step with no retry, so it sometimes ran while
  the static assets were live and the Functions were not yet at the edge, failing a
  commit whose functions were fine.
- **The database proofs printed `FAIL` for the outcome they wanted.** t75 asked the
  database to refuse a stranger deciding a proposal, ran that through `as()` — which
  records a failure whenever the statement throws — and then asserted the result was
  null. Seven checks in that file were written this way, so a correct refusal printed
  `FAIL` while the `ok` came from the assertion beside it. The harness still passed,
  because it tracked a private counter and never consulted what the shared library
  had recorded. The loud symptom trains a reader to skim `FAIL`; the quiet one is a
  real failure recorded in the library that no exit status examined. t39 and t40 had
  the same blind exit. Refusals now go through `expectFail` with the error code they
  must raise, `failureCount()` is folded into every harness's exit status, and a
  deliberately wrong expected code has been shown to turn the harness red.
- **The test count was a silent zero in a clean checkout.** H-01 ran `vitest` in all
  sixteen packages and reported `main-site 0` while 1169 tests were passing, because
  a package with no `node_modules` exits without a summary line and the parser read
  that as "no tests". The number now names a package as uncounted rather than
  counting it as empty.
- **Two review counts were the last ASCII digits in the marketplace.** A member
  reading Bangla saw a Bangla shop name with an English `(7)` beside its stars.
  Every other number goes through `BanglaDigitFormatter`; these two now do as well.
- **A proof harness that is present is not a proof harness that runs.** `run.mjs`
  said a dropped-in `tNN.mjs` runs on its own. It does not — the file must be listed
  in `HARNESSES`, and an unlisted one is skipped in silence. The comment now says so,
  and `t76` proves 0116 and 0117 behaviourally: a variant of a picture the product
  does not show is refused, a plaintext variant is refused, a save that omits the
  field keeps the stored map, replacing the images prunes the removed picture's
  variant, and `updated_at` advances rather than the trigger merely existing.
- **Four checks were measuring the wrong thing.** C-05 scanned a vendored Leaflet file
  for a fixed width that cannot reach a page layout; D-09 matched the *script* that
  keeps the keystore out of the repository; C-01 and E-11/E-12 were reported failing
  without a `dist` to read. The first two are now scoped to what they meant to test,
  and the last three pass once a build exists. C-01's two real findings were fixed
  rather than exempted.
- **Three internal writers were answering the door.** B-05 derives "what anon can
  execute" from explicit `grant … to anon` lines, which cannot see Postgres's
  default EXECUTE to PUBLIC. Asked the catalogue directly with
  `has_function_privilege`, three security-definer writers in the `bsdc` schema
  were callable by an anonymous visitor: the three-argument `bsdc.audit` overload
  (0024, never revoked — 0068 revoked only the four-argument one), and
  `bsdc.note_deployment` / `bsdc.resolve_deployment_note` (0056, which postdates
  0049's hand-written list). An anonymous visitor could forge audit rows, overwrite
  a recorded deployment fault and reopen it, or mark a live fault resolved. All
  three are now revoked from PUBLIC, anon and authenticated; the catalogue was
  checked first to confirm no policy, default, constraint, index, or SECURITY
  INVOKER function needs them, and `t77` proves the refusal, the owner's continued
  access, and that the read-only policy helpers still answer. A first attempt at a
  catalogue-wide sweep broke real writes (`join_text`, `normalise_skills`,
  `can_post_in_channel`, `mk_owns_vendor` are called as the caller from
  constraints and invoker functions), which is why 0118 revokes exactly the three
  confirmed holes and no more.

## What no checkpoint can settle

Everything in this section is recorded here rather than dressed up as an automated result.

**Whether the Bangla reads naturally.** A test can prove that both locales
carry the same keys and that the Bangla file contains 25,133 Bangla code
points. It cannot prove that a sentence sounds like something a person from
Sylhet would say. That needs a native reader, and it is the first thing to
put in front of one.

**Whether the honest answers are the right answers.** The platform refuses
to dress noise up as a forecast, reports speed at the 75th percentile with
its sample count, labels a route with fewer than twenty samples as not yet
worth believing, and tells a member why a moderation decision was taken. A
checkpoint can prove the code does these things. Only a person can decide
they are the right things to do.

**Whether the thresholds are right.** 250 KB of initial JavaScript, 4.5:1
contrast, a one-hour response target for a safety report, twenty samples
before a route is ranked: each is defensible and each is a choice. They are
written in one place each — the budget in CI, the contrast in
`domain/brand.ts`, the targets in `domain/moderation.ts`, the sample floor
in `domain/perf.ts` — so changing one's mind is a one-line change rather
than an archaeology project.
